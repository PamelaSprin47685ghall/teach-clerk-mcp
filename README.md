# Teach Clerk MCP

An AI teacher with exactly one MCP tool and an executable, append-only Clerk
whiteboard. Many students can learn at once in **one Java process**. Each
browser tab owns a private, in-memory Clerk Notebook.

## Student workflow

1. Connect the MCP URL to ChatGPT using **OAuth**. No API key or OAuth client
   credentials need to be entered. Confirm the browser consent screen.
2. Open https://teach-clerk-mcp.onrender.com/ in another browser tab.
   A private Notebook and a six-digit pairing code appear.
3. Copy the prompt into ChatGPT: **我的配对码是 XXXXXX，请使用 @Teach Clerk 让我学习:**
   Replace XXXXXX with the code in that tab. Append the desired lesson goal.
4. ChatGPT calls the sole tool, teach_then_ask, with pairing_code and source.
   The source is a Clojure expression which evaluates to Clerk content.
5. The tool waits for the student to type an answer or choose Skip. Repeating
   this call with the same code builds the lesson. Sending source = null ends
   that student's lesson.

The browser tab, not an account, identifies the student. Every page load
creates an independent, ephemeral room. Closing the tab sends a cleanup
message, and abandoned rooms have a 20-minute idle timeout. Pairing binds
the room to the first anonymous OAuth grant that uses its code.

## MCP API

Endpoint: https://teach-clerk-mcp.onrender.com/mcp

The single tool is named teach_then_ask. It accepts:

    {"pairing_code": "123456",
     "source": "(clerk/md \"## 今天我们学习乘法\")"}

It waits for a student reply and returns student_reply as a string or null.
Each student's wait is independent. The teacher Agent owns GOAL, role,
teaching framework and cadence; the MCP server does not call an LLM.

### When a student takes longer to answer

The default tool wait is **20 seconds** (override with the
STUDENT_REPLY_TIMEOUT_MS environment variable, clamped to 1–25 seconds).
This is shorter than typical external MCP tool deadlines. If the student
has not answered, the tool returns a successful observation:

    {"status": "student_timeout",
     "student_still_thinking": true,
     "must_call_again": true,
     "closed": false}

This does NOT mean the student clicked Skip (which returns a literal null
student_reply) or gave a wrong answer. The teacher receives a mandatory
instruction to call teach_then_ask again with the **same pairing_code**
and a non-null teaching source, adapting patiently rather than abruptly
ending the lesson or revealing the answer. Calling source=null is rejected
until the teacher has actually published a follow-up lesson action.

The student textbox remains enabled after the timeout. If the student
answers after the first tool result was delivered, their answer is saved
and the teacher's next tool call returns status=late_student_reply
instead of rendering an obsolete hint. The teacher must subsequently
call teach_then_ask again to react to this genuine answer.
For a quiet, non-leading extra waiting window, the teacher can use
source = "(clerk/fragment)": this is a valid non-null teaching action
that waits again **without adding visible content to the whiteboard**.
There is no background LLM request and no extra JVM.

## Example generated by the teacher

    (clerk/fragment
      (clerk/md "## 九九乘法表")
      (clerk/table
        (mapv (fn [i]
                (mapv (fn [j]
                        (if (<= j i)
                          (str j " × " i " = " (* i j))
                          ""))
                      (range 1 10)))
              (range 1 10)))
      (clerk/md "观察第七行，相邻两个乘积相差多少？"))

Viewer types: md, tex, code, table, restricted Hiccup/SVG html,
plotly, vl, fragment, row, and col.

## Isolated, incremental Clerk Notebooks

One Clerk Notebook template is initialized when Java starts. Each browser
tab gets an independent in-memory document based on that template. Clerk's
own Viewer presents its content. Each update computes an Editscript diff
against that student's last presentation and sends the Clerk patch-state!
message only over that student's WebSocket. No full page reload, no global
broadcast, no re-evaluation of old teacher programs. Generating a diff still
traverses the document, so processing cost grows with lesson length.

## OAuth

The server publishes protected-resource discovery, authorization-server
metadata, DCR, S256 PKCE, authorization-code and refresh-token grants.
Issuer, audience, expiry, and teaching scope are checked on each tool call.
There are no static MCP keys. The browser consent screen creates an anonymous
OAuth principal; this is not a verified real-world identity or an account.
The paired room is bound to the principal created by the OAuth consent.

## Run and test

Requires Java 21+ and the Clojure CLI:

    export PORT=10000
    export PUBLIC_BASE_URL=http://127.0.0.1:10000
    export OAUTH_SIGNING_SECRET="$(openssl rand -hex 32)"
    clojure -M:run

    clojure -M:test
    node --check resources/public/classroom.js
    bash scripts/oauth_smoke_local.sh
    bash scripts/timeout_smoke_local.sh

The smoke test covers OAuth, token refresh, code replay, two concurrent
lessons, private answers and Notebook isolation. When Node's ws package is
available, run node scripts/ws_smoke.cjs to validate WebSocket diff isolation.

Render uses the Dockerfile, render.yaml and a generated signing secret.
Render sets RENDER_EXTERNAL_URL, so PUBLIC_BASE_URL is optional in production.

## Limits and safeguards

This is a prototype, not a hardened multi-tenant service. The SCI interpreter
shares the single JVM with all Notebooks. It blocks common unbounded forms,
limits range sizes, output sizes, and evaluation time, and uses a bounded
worker pool. **It is not a security sandbox against hostile code.**

In-memory lesson state, pairing codes and pending OAuth codes are lost on a
restart. Signed access/refresh tokens stay valid while the OAuth signing
secret is unchanged; rotating it revokes all grants. The room limit is 120.
Each Notebook also has a one-million-character stored-content budget.
Render's free instance can sleep, restart, or run out of memory under load.
